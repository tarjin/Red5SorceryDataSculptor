5. E-02 — Historical MAP health gate

ACCEPTED BY T / FROZEN FOR SUCCESSOR PRD INTEGRATION

The Store-lineage health gate applies regardless of which Store MAP is explicitly named.

  1. An explicitly named current or historical Store MAP may be used only when the Store lineage is currently VALID.
  2. Every RID/COL binding referenced by the named MAP must be currently present and valid.
  3. If either condition fails, Data Sculptor refuses the operation. An older MAP cannot be used to hide present lineage damage.
  4. The same rule applies when UPDATE ALIASES uses a historical Store MAP as its base.

This preserves deliberate historical-state reproduction without creating an escape from current Store health or publication-validity rules.

6. P3-03 — Current WKO MAP selection and repair-required trigger

ACCEPTED BY T / INTEGRATED INTO REVISION BM

WKO MAP structural validity and present registry health are now distinct concepts.

  1. Only structurally valid WKO MAP artifacts participate in current-registry selection.
  2. Among structurally valid WKO MAPs, the greatest canonical UTC millisecond timestamp identifies the current WKO MAP; an equal-greatest timestamp tie refuses.
  3. A current structurally valid WKO MAP remains current even if one or more referenced physical WKO files are missing.
  4. The registry is repair-required exactly when that current structurally valid WKO MAP contains at least one row whose referenced physical WKO file is missing.
  5. Missing referenced WKOs do not cause silent fallback to an older WKO MAP; alias authority therefore does not roll backward merely because a file disappears.
  6. A structurally malformed newer WKO MAP never becomes current. Data Sculptor falls back to the greatest earlier structurally valid WKO MAP, if one exists, and reports the malformed newer artifact through Help/evidence surfaces.
  7. The governed REPAIR WORK ORDER REGISTRY path remains the repair route for missing-reference damage in the current structurally valid WKO MAP.

8. P3-05 — Help exits for INVALID and all-COLs-broken DEGRADED Store lineages

ACCEPTED BY T / INTEGRATED INTO REVISION BM

The Store-health architecture is unchanged: ordinary materialization must not silently treat a known damaged lineage as unseen, an INVALID Store does not gain an invented recovery operation, and an all-COLs-broken DEGRADED Store cannot publish a zero-COL successor MAP. P3-05 freezes the analyst-facing exits that Help must explain.

  1. Help must identify the exact blocked Store lineage and current Store MAP.
  2. For an all-COLs-broken DEGRADED Store, Help must explain that structural MAP repair cannot remove every mapped COL. The analyst may externally restore at least one governed COL artifact under its original physical filename; Data Sculptor validates it under the tier required by the next operation before it can re-enter use, after which Store health can be re-evaluated and REPAIR MAP may become available.
  3. For an INVALID Store, Help must explain that the analyst may externally restore a governed RID artifact under its original physical filename; Data Sculptor validates it under the tier required by the next operation before it can re-enter use, after which Store health can be re-evaluated. This is external restoration, not RID regeneration by Data Sculptor, and filename equality does not prove historical byte identity.
  4. For either blocked state, the analyst may rename the source file and materialize the renamed source to deliberately begin a new Store lineage with a new RID. This does not repair, replace, erase, or supersede the damaged lineage.
  5. For either blocked state, the analyst may retire the damaged lineage from active Suitcase routing by moving all Store MAP artifacts belonging to that lineage out of the Suitcase root. Help must warn that moving only the latest MAP is insufficient because an older structurally valid MAP could otherwise become current.
  6. Renaming the source and retiring the lineage are distinct choices: rename preserves the damaged lineage in the active Suitcase while creating a separate lineage under a different source identity; moving all lineage MAPs out removes that lineage from active routing while preserving the moved artifacts wherever the analyst chooses to keep them.
  7. No new Data Sculptor command, automatic deletion, automatic retirement, RID regeneration, or silent lineage fork is introduced by this decision.

9. P3-06 — RID/COL validation depth and restoration assurance boundary

ACCEPTED BY T / INTEGRATED INTO REVISION BM

P3-06 closes P2-04 by defining the depth of governed artifact validation and by removing the unprovable claim that a file restored under the same physical filename is necessarily the historical original bytes.

  1. Tier 1 — Store-health structural validation. Routine Store status, routing, historical-MAP health gates, inheritance decisions that do not consume artifact contents, and alias-only maintenance use bounded structural checks. The Store MAP is fully structurally validated. RID Tier 1 checks the exact bound filename, readability, UTF-8 BOM, canonical N=<value> header, final LF, and deterministic physical byte length implied by canonical RID serialization. COL Tier 1 checks the exact bound filename, readability, UTF-8 BOM, exact decoded one-column header against the MAP source_header, and final LF. Tier 1 does not rescan all RID/COL data records merely to perform routine status or alias work.
  2. Tier 2 — full artifact validation. Any operation that consumes RID/COL contents, complete validation of newly created candidates before commit, and REPAIR MAP use full streaming validation. RID Tier 2 proves the canonical header, exactly N records, and exact 1..N sequence. COL Tier 2 proves canonical one-column CSV form, exact expected header, and exactly N aligned logical data records.
  3. REPAIR MAP determinism. Once repair is validly entered, the RID and every mapped COL that could survive are Tier-2 validated. The successor removes exactly the COL bindings that fail that full check, subject to the separately frozen all-COLs-broken refusal. The same bytes therefore yield the same repair set.
  4. Restoration boundary. A file restored under an original governed RID/COL filename may re-enter use only after passing the validation tier required by the operation. WASM-002 does not infer historical byte-for-byte identity from filename equality. Stronger identity requires separate authoritative fingerprint evidence.
  5. No Store-MAP schema expansion. P3-06 does not add SHA-256, byte-length, or other per-artifact identity fields to the nine-column Store MAP.
  6. F-04 prerequisite integrated. Because Tier 1 reads the already-frozen RID cardinality metadata, BM now integrates F-04's canonical RID header N=<value> and updates the canonical RID golden-byte acceptance fixture.

10. P3-07 — Routable Store lineage and all-MAPs-damaged anti-fork boundary

ACCEPTED BY T / INTEGRATED INTO REVISION BM

P3-07 closes the remaining routing hole in which a Store could disappear from discovery merely because every Store MAP in its lineage had become structurally damaged.

  1. One routing term. A routable Store lineage is a lineage for which at least one structurally valid Store MAP exists. This routing term is independent of Store health: VALID, DEGRADED and INVALID lineages remain discoverable and are evaluated after routing.
  2. No health-driven disappearance. Referenced RID/COL damage may cause refusal, but it must not make a lineage with a structurally valid Store MAP vanish from source routing.
  3. All-MAPs-damaged guard. If exact-SOURCE routing finds no routable lineage while one or more structurally malformed Store-MAP-class artifacts are present in the active Suitcase, ordinary materialization must refuse before creating a new Store or RID.
  4. No inference of nonexistence. Data Sculptor must not interpret the absence of a structurally valid Store MAP as proof that no prior Store lineage existed when malformed Store-MAP-class artifacts remain visible.
  5. Help duty. The refusal must identify the malformed Store MAP artifact or artifacts that triggered the guard and explain that new-Store creation was blocked to prevent a silent lineage fork. This decision does not invent a new repair/replacement operation.
  6. CAT boundary preserved. CAT may later orient across MAP-governed Stores, but it is not Store-lineage authority and is not used to bypass this routing/refusal rule.

11. P3-08 — Windows-1252 CVT source identity and Store-lineage boundary

ACCEPTED BY T / INTEGRATED INTO REVISION BM

P3-08 resolves the asymmetry created by governed conversion: every conversion publishes a new CVT filename, while Store routing is intentionally based on exact source identity.

  1. CVT is a new source artifact. Every successful CONVERT_WINDOWS_1252_TO_UTF_8 run publishes one new immutable governed CVT with its own exact physical filename.
  2. Exact CVT filename is the routing identity. Later materialization uses that exact CVT filename as the Store-routing source identity. The analyst-owned pre-conversion filename is not carried forward as hidden Store-lineage identity.
  3. No inferred continuity across conversions. Two separate CVT artifacts are separate source identities even when both conversions began from analyst-owned files having the same original filename. A later refreshed legacy source therefore does not silently refresh or replace an earlier CVT-backed Store.
  4. First materialization consequence. First materialization of a distinct CVT begins a new Store/RID lineage unless that exact CVT filename already routes to an existing lineage under the ordinary Store rules.
  5. Help disclosure. On conversion success, Help must say that the CVT is a new governed source identity and that a later reconversion creates another distinct CVT rather than refreshing the earlier lineage. When a CVT is selected for first materialization, Help must disclose the same consequence and must not imply lineage continuity through the original analyst-owned filename.
  6. No larger identity mechanism. WASM-002 does not add original-source lineage metadata, hidden conversion ancestry routing, or a new Store-linking mechanism to solve this case.

Primary BM targets: W002-STOR-019.2, W002-CONV-003, W002-CONV-004, W002-CONV-ACC-001, W002-UI-008.

12. P3-09 — No-header-record structural CSV refusal

ACCEPTED BY T / INTEGRATED INTO REVISION BM

P3-09 closes the deterministic-oracle gap for a Stage-1-certified source that contains no logical CSV record at all.

  1. New exact token. The frozen structural malformed-CSV condition-token set is extended by exactly one token: NO_HEADER_RECORD.
  2. Trigger. The token applies when Stage 1 has certified the source and Stage 2 reaches end-of-source without establishing any logical CSV record from which the required header could be parsed.
  3. Exact location oracle. Source-byte offset equals the exact source byte length; physical line = 1; logical record = 1; field ordinal = 1.
  4. Two required byte forms. A zero-byte source therefore reports offset 0. A source containing only the UTF-8 BOM bytes EF BB BF reports offset 3. Both refuse as NO_HEADER_RECORD.
  5. Blank-record distinction. A first logical record that exists but is blank remains governed by the already-frozen BLANK_LOGICAL_RECORD condition; it is not reclassified as no-header-record.
  6. Durable evidence. The MATERIALIZE Receipt serializes the token and all four exact location facts in the already-frozen CSV refusal fields, and byte-exact/golden fixtures cover both required byte forms.

Primary BM targets: W002-MAT-001.7, W002-MAT-003.2, W002-MAT-ACC-003, W002-RCP-007.
